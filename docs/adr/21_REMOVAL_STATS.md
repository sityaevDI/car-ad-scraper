# Removal stats — статистика снятых объявлений

Реализует первый кусок "Historical analytics" из `06_SEARCH_MARKET.md` §9–11 без market price/confidence
(они по-прежнему вне MVP, см. `03_FRONTEND.md` §7). Страница: `/market/removed`, API:
`GET /api/v1/market/removed-stats?period=day|week|month&make=`. Публичная, без auth.

## 1. "Снято", а не "продано"

Факта продажи у нас нет — только `Listing.status = REMOVED` (объявление пропало с источника, см.
`ListingRepository.mark_missing_as_removed`; помечает только `FULL_SOURCE_REFRESH`). По
`06_SEARCH_MARKET.md` §10–11 UI обязан это проговаривать, поэтому везде "снято с публикации", а над
метриками — плашка-оговорка. "Срок на рынке" — `last_seen_at − first_seen_at`, то есть время, которое
*мы* видели объявление, а не время жизни на площадке (объявления, уже висевшие до первого скрейпа,
занижены).

**Дата снятия = `last_seen_at`**, а не момент, когда краулер заметил пропажу: `removed_at` в модели нет,
а `last_seen_at` ближе к реальному моменту ухода. Следствие: день можно досчитать задним числом, когда
следующий полный краул заметит пропажу, — поэтому пересчёт идемпотентный (§3).

## 2. Метрики

На окно (`period_days` суток по UTC, заканчивающееся `stat_date`) и скоуп (всё / марка / марка+модель):

- `removed_count`;
- `median_days_on_market`;
- `median_price_at_removal` (`Listing.price` на момент снятия);
- `price_cut_share` — доля снятых, у которых цена падала относительно первого снапшота;
  `median_price_cut_pct` — медианная глубина снижения среди них (запас на торг).

Для сравнения "к прошлому периоду" считается и предыдущее окно (week/month). Ряд по дням — 30
`period_days=1` строк. Строка модели пишется только при `removed_count >= 3` (`MIN_MODEL_REMOVED`):
на 1–2 объявлениях статистика по модели ничего не говорит. Окна считаются по **последним полным суткам**
(вчера, UTC) — сегодняшний неполный день не портит график.

## 3. Как считается (почему не на лету)

Агрегация тяжёлая (снапшоты + медианы по всем маркам/моделям), а данные меняются раз в краул, поэтому
это витрина `removal_stats` (`app/models/removal_stats.py`), которую пересобирает arq-cron в
scrape-воркере (`app/market/removal_stats.py`): **в 03:10 и 15:10 UTC и при старте воркера** (чтобы после
деплоя страница не была пустой до ближайшего слота). API читает готовые строки и Listing не трогает.

Вручную (после первого создания таблицы или пропущенного запуска): `python -m app.market.removal_cli refresh`.
Стартовый запуск воркера ненадёжен при выкатке: старый воркер, ещё не остановленный, может забрать задачу
из общей очереди Redis и упасть с `function not found`.

Пересчёт: один запрос по снятым за последние ~60 дней → медианы в Python (независимо от диалекта, тесты
идут на sqlite) → `DELETE` строк тех же `(stat_date, period_days)` + `INSERT` в одной транзакции.
`make`/`model` в витрине — `""` для "все" вместо `NULL`, чтобы unique-констрейнт работал.

## 4. Ограничения / на потом

- Один общий скоуп по всем источникам и без учёта валюты — пока источник один (EUR). При появлении второго
  источника/валюты нужен `source_id` (и/или валюта) в ключе витрины.
- Ряд по дням только для "все марки" и отдельной марки, не для модели (слишком разреженный).
- Качество зависит от полноты полных краулов: частично заблокированный краул исказит "снято".
- Пересчёт витрины — cron в воркере, а не `ScheduledScrape`, поэтому в админке его не видно и упавший
  пересчёт никак не заметен. Нужен общий блок "фоновые задачи", см. `13_ADMIN.md` → Background jobs.
- Модельные фильтры (поколение, год, пробег), price score и confidence — не здесь, см. `06_SEARCH_MARKET.md`.
